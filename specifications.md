# MedTracker — Backend Design & Implementation Guide

> Raw specification and implementation instructions to hand to an AI (or engineer) to build a production-ready backend for a medication tracking & health metrics app.

---

## Overview / Goals

MedTracker is a medication tracking application for patients and caretakers. The backend should be a **Django + Django REST Framework (DRF)** API using **PostgreSQL**. Use **Djoser + SimpleJWT** for authentication. Use **Celery + Redis** for background tasks like reminder generation and notification delivery.

Primary goals:

- Simple, robust, and secure API for Flutter frontend.
- Intuitive models for users, caretakers, medicines, schedules, reminders, intakes, and health metrics.
- Support complex recurring schedules (RRULE), timezone-aware reminders, snooze/dismiss, and auditability.
- Scalability: efficient indexes, background workers, and clear deployment guidance.

Audience: An AI or developer that will implement the backend. This document provides full context, DB design, API contracts, background task behavior, and production considerations.

---

## High-level Entities

- **User (custom Django user)** — primary account with email-based auth. Optional profile fields (phone, address, profile image, timezone).
- **Caretaker** — person who can help a user; stored as its own table (not necessarily an app user). Users may have multiple caretakers.
- **UserCaretaker** — link table between user and caretaker with permission flags.
- **Medicine** — user-specific medicine record.
- **MedicineAttribute** — details about medicine (form, composition, dose info); flexible JSON for composition.
- **Schedule** — when to take medicine. Support `time`, `date`, optional `rrule` for recurrence, `timezone`, `dose` overrides.
- **Reminder** — scheduled notifications derived from `Schedule` (caches next occurrences, status, snooze, triggered_at, resolved_at).
- **Intake** — record when a user (or caretaker) confirms medication intake (or misses it).
- **HealthMetric** — user metrics like blood_pressure, blood_sugar stored as JSON.
- **MetricReading** — timestamped readings linked to HealthMetric (or metric_key).
- **PushSubscription** (optional) — store push endpoints for FCM/APNs/web.
- **AuditLog** (optional) — versioned changes for critical actions.

## Database Schema (Postgres) — integer primary keys

Use `INTEGER` auto-increment primary keys (Postgres `SERIAL` or `GENERATED BY DEFAULT AS IDENTITY`). Keep schema compatible with earlier design decisions.

### Tables (summary)

- users (custom auth model — `accounts.User`) — id SERIAL PK
- caretakers — id SERIAL PK
- user_caretakers — id SERIAL PK, user_id FK, caretaker_id FK, permission flags
- medicines — id SERIAL PK, user_id FK, name, image, brand, start_date, until, created_at, updated_at
- medicine_attributes — id SERIAL PK, medicine_id FK, user_id FK, type (enum), composition JSONB, dose, dose_unit, schedule_id FK (nullable)
- schedules — id SERIAL PK, medicine_id FK, user_id FK, timezone, time, date, end_date, rrule (text), instruction, dose_amount, dose_unit, dose, note
- reminders — id SERIAL PK, schedule_id FK, status enum, next_run timestamptz (important), snooze_until, triggered_at, resolved_at
- intakes — id SERIAL PK, user_id FK, medicine_id FK, schedule_id FK (nullable), reminder_id FK (nullable), status enum, scheduled_time, taken_at, recorded_by, note
- health_metrics — id SERIAL PK, user_id FK, name, data JSONB, recorded_at
- metric_readings — id SERIAL PK, user_id FK, metric_id FK (nullable), metric_key, recorded_at, values JSONB
- push_subscriptions — id SERIAL PK, user_id FK, platform, endpoint, keys JSONB
- audit_logs — id SERIAL PK, user_id FK, actor, action, object_type, object_id, before JSONB, after JSONB, created_at

**Important fields**

- `schedules.rrule` — RFC5545 text for recurrence (optional). If not present, schedule uses `time` + `date` as a single occurrence.
- `reminders.next_run` — store the next UTC timestamp to trigger (main index for worker).

**Indexes**

- reminders(next_run) WHERE status = 'pending' (partial index) — for worker selection.
- medicines(user_id), schedules(user_id, medicine_id)
- intakes(user_id, taken_at DESC)
- metric_readings(user_id, metric_key, recorded_at DESC)
- GIN indexes on JSONB columns frequently queried (medicine_attributes.composition, metric_readings.values)

## Django Models (requirements)

- Use a **custom User model** `accounts.User` (email as `USERNAME_FIELD`). Provide `full_name`, `phone_number`, `address`, `profile_image` (ImageField), `timezone` default `Asia/Kathmandu`.
- Implement `Caretaker`, `UserCaretaker` models as above, with `unique_together` constraint on `(user, caretaker)` to avoid duplicate links.
- Store JSON with `models.JSONField` (Django built-in) to keep flexible attributes.
- Use `choices` for enums (medicine form, reminder_status, intake_status).
- Keep `auto_now_add` and `auto_now` timestamps where appropriate.

Note: For ImageFields include `Pillow` in requirements and configure `MEDIA_ROOT` & `MEDIA_URL`.

## API Design (DRF + Djoser + SimpleJWT)

### Auth

- Use **Djoser** for registration endpoints and **SimpleJWT** for JWT tokens.
- Djoser serializer mapping in settings:

    ```py
    DJOSER = {
      'USER_CREATE_PASSWORD_RETYPE': True,
      'SERIALIZERS': {
        'user': 'accounts.serializers.UserSerializer',
        'user_create': 'accounts.serializers.UserCreateSerializer',
        'current_user': 'accounts.serializers.UserSerializer',
      }
    }
    ```

- `/api/auth/jwt/create/` → login (returns access & refresh)
- `/api/auth/users/` → register (via Djoser)
- `/api/auth/users/me/` → current user

### Main endpoints (suggested)

- `GET /api/medicines/` — list user's medicines

- `POST /api/medicines/` — create

- `GET /api/medicines/{id}/` — retrieve

- `PUT/PATCH /api/medicines/{id}/` — update

- `DELETE /api/medicines/{id}/`

- `GET /api/medicines/{id}/attributes/` — list attributes

- `POST /api/medicine-attributes/` — create attribute for a medicine

- `GET /api/schedules/` — list schedules (user-scoped)

- `POST /api/schedules/` — create schedule (accept rrule or single date/time)

- `GET /api/schedules/{id}/` — retrieve

- `GET /api/reminders/` — upcoming reminders (user-scoped)

- `POST /api/reminders/{id}/snooze/` — snooze

- `POST /api/reminders/{id}/dismiss/` — dismiss

- `GET /api/intakes/` — intake logs

- `POST /api/intakes/` — record intake (taken/missed)

- `GET /api/health-metrics/` — list

- `POST /api/health-metrics/` — create

- `GET /api/metric-readings/` — list readings

- `POST /api/metric-readings/` — create reading

- `GET /api/accounts/caretakers/` — list caretakers linked to user

- `POST /api/accounts/caretakers/` — create + link

- `POST /api/accounts/caretakers/link-existing/` — link existing caretaker by id

### API behaviors

- **All endpoints must be user-scoped**: users see only their data unless `is_staff`.
- **Create endpoints** should assign `user=request.user` server-side; clients should not trust passing user IDs.
- **Pagination**: use `LimitOffsetPagination` or `PageNumberPagination` with default page size.
- **Filtering & searching**: allow filtering medicines by `name`, `brand`; schedules by `medicine_id`; readings by `metric_key` and date ranges.
- **Validation**: `Schedule` must validate `date/time` and `rrule` consistency. If `rrule` present, ensure `time` and `date` are consistent or clarify expected behavior in docs.

## Reminder & Recurrence Implementation

### Design choices

- Store `Schedule.rrule` (RFC5545 string) when recurrence is needed. For simple daily/weekly schedules, client may send human-friendly parameters OR RRULE.
- **Worker approach (recommended)**: store a `reminders` table that caches next occurrence(s). Keep `reminders.next_run` (UTC) for efficient querying.

### Flow

1. When a `Schedule` is created/updated:
    - If `rrule` present: expand next N occurrences in user's timezone (use `python-dateutil` `rrule` or `rrule` library) — compute next 1 or 7 occurrences.
    - Create `Reminder` rows for the next occurrences or update a single `reminder` row with `next_run` timestamp.

2. Celery Beat / periodic job (e.g., every minute):
    - Query `Reminder` with `status='pending'` and `next_run <= now()` (and `snooze_until` conditions).
    - For each due reminder: send notification (FCM/APNs/SMS/email), set `triggered_at = now()`, mark as `pending->triggered` or update accordingly.
    - After sending, compute next occurrence (from RRULE or schedule) and update `next_run`. If no further occurrence, mark reminder inactive or remove.

3. When user taps **Taken** in client: create `Intake` record with `taken_at=now()` and update corresponding `Reminder.status='taken'`, `resolved_at=now()`.
4. Support `snooze` by updating `snooze_until` on the `Reminder` and keeping status `snoozed`.

### Timezones

- Always store timestamps in UTC in DB. Convert to user's timezone for display and rrule expansion.
- Keep `Schedule.timezone` (IANA string) and `User.timezone`.

### Tolerance windows

- When matching intakes to scheduled times, allow a configurable tolerance window (e.g., 30 minutes before/after scheduled_time) to count as "on-time".

## Background Worker & Tasks (Celery)

- **Celery broker**: Redis (recommended). Celery Beat for periodic tasks.

- Tasks to implement:
    - `expand_schedule_rrule(schedule_id)` — generate next occurrences and write reminders.
    - `process_due_reminders()` — find reminders due, send notifications, update `triggered_at`, schedule next run.
    - `send_push_notification(user_id, payload)` — wrapper around FCM/APNs; use separate service for retries.
    - `cleanup_old_intakes()` — archive or delete old intakes per retention policy.

- **Retries & Idempotency**: make tasks idempotent. Use distributed locks for scheduling updates to avoid double-sends.

## Notifications

- Use **FCM** for Android and web push; **APNs** for iOS.
- Backend stores `PushSubscription` model (endpoint, keys, platform) for each device linked to user.
- When a user registers their device, create a `PushSubscription` row.
- For SMS fallback (optional), integrate with Twilio or local SMS provider — enforce rate limiting.

## Security & Compliance

- **Authentication**: Djoser + SimpleJWT. Use HTTPS in production.
- **Passwords**: use Django defaults (PBKDF2) or configure Argon2 if required.
- **Authorization**: server must enforce object-level permissions (users can only access their own data, caretakers only if linked and with permission flags).
- **PII Protection**: consider encrypting extremely sensitive fields at application level (e.g., health identifiers).
- **Logging & Auditing**: store audit logs for modifications to schedules, medicines, and caretaker links. Keep immutable `intakes`.
- **HIPAA/GDPR considerations**: implement data retention & deletion workflows; consent management if applicable.

---

## Performance & Scaling

- Use proper indexes (see Indexes section above).
- Use read replicas for heavy read workloads (dashboards). Offload heavy reports to worker tasks.
- Consider partitioning `intakes` and `metric_readings` by `user_id` or by time if the data grows huge.
- Cache next upcoming reminders in Redis for UI features.

## Deployment & DevOps

Minimum production environment:

- PostgreSQL (managed or provisioned)
- Redis (for Celery)
- Gunicorn + Nginx
- Celery worker(s) + Celery Beat
- S3-compatible object storage for media (profile images, attachments)
- HTTPS with TLS certs (Let's Encrypt)

Suggested artifact structure: Docker + docker-compose with separate services:

- web (Django + Gunicorn)
- worker (Celery)
- beat (Celery Beat)
- db (postgres)
- redis
- nginx (reverse proxy)
- optional: minio or use S3

**Environment variables** (minimum):

- DJANGO_SECRET_KEY, DEBUG, ALLOWED_HOSTS
- DATABASE*URL or POSTGRES*\* vars
- REDIS_URL
- DJOSER / SIMPLEJWT settings if customization needed
- FCM_SERVER_KEY or APNS credentials
- S3_BUCKET / AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY

```http

Content-Type: application/json
{
  "email": "alice@example.com",
  "full_name": "Alice Example",
  "password": "SuperSecret1",
  "phone_number": "+97798123..."
}
```

### Login

```http
POST /api/auth/jwt/create/
{
  "email": "alice@example.com",
  "password": "SuperSecret1"
}
```

### Create medicine

```http
POST /api/medicines/
Authorization: Bearer <token>
{
  "name": "Paracetamol",
  "brand": "Acme",
  "start_date": "2025-10-10",
  "until": "2025-10-20"
}
```

### Create schedule with RRULE (daily at 08:00 and 20:00)

```http
POST /api/schedules/
Authorization: Bearer <token>
{
  "medicine": 5,
  "time": "08:00:00",
  "date": "2025-10-10",
  "rrule": "FREQ=DAILY;BYHOUR=8,20;BYMINUTE=0",
  "timezone": "Asia/Kathmandu"
}
```

### Create intake (user taps Taken)

```http
POST /api/intakes/
Authorization: Bearer <token>
{
  "medicine": 5,
  "schedule": 2,
  "reminder": 10,
  "status": "taken",
  "taken_at": "2025-10-10T02:15:00Z"
}
```

## Handover notes for the AI / Developer

When you hand this spec to an AI (or developer), instruct it to:

1. Create a Django project skeleton with `accounts`, `medicines`, `reminders` (or single `api`) apps. Use `accounts.User` as custom user model.
2. Implement models exactly as described with integer primary keys.
3. Add serializers, viewsets, and routers for all endpoints, with `perform_create` assigning `request.user` where relevant.
4. Integrate Djoser and SimpleJWT for auth; add necessary serializers (`UserSerializer`, `UserCreateSerializer`).
5. Set up Celery tasks for rrule expansion and reminder processing; ensure idempotency and distributed lock protection.
6. Add tests for reminder lifecycle, schedule creation, and intake recording.
7. Prepare `docker-compose.yml` with services: web, db, redis, worker, beat, nginx, and optionally minio.
8. Provide documentation (OpenAPI/Swagger) for all endpoints.
